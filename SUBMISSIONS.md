# Private completed-plan submissions (RPA-64)

This implementation is off by default. It adds a Send action, shared active-form validation, private R2 persistence and an operator CLI. It does not provision storage, activate billing, enable a live collection, deploy the app or change AI settings. Max approved the R2 choice and submission contract on 14 September 2026. Operational activation remains a separate decision.

RPA-151 upgrades the active contract to `rpa-active-2026-09-17-v2`. Recovery backups and incomplete local drafts use version 11 and retain browser identity, stable `planId`, and any sequential-review record. New completed-plan snapshots retain the ordered studies and named researchers shown in the active form. Historical v1 records/receipts remain readable, and a frozen pending v1 browser request is retried unchanged rather than converted under its existing submission ID. RPA-83 owns public access and abuse readiness.

## MVP compatibility decision — 15 September 2026

Max selected the previously tested two declarations and final Send for the MVP. When submissions are enabled, the review step shows those four existing controls and the submission receipt panel. The sequential sign-off UI remains in draft-only mode. A late configuration response moves the existing controls without rebuilding the plan or losing typed sign-offs.

The RPA-99 email entry still checks the address independently of plan completion. Its MVP wording explains local draft/backup identification and does not promise email delivery. The email address and the RPA-139 workflow record (parties, history and review notes) stay in local drafts/backups; neither is collected by this policy. A previous workflow approval is reopened locally if its content changes in the MVP, preserving its ledger rather than leaving an approval on changed text.

The v2 wire schema is explicit rather than a silent expansion of v1. RPA-98's dormant comments slot remains empty in new projections; historical frozen v1 requests and receipts retain their original comments. The validator explicitly recognises the active form and the separate email entry page. Unexpected fields still block Send. Restoring an operator export recovers the collected plan and declarations, not browser-only identity or review history.

Automated integration evidence is separate from the earlier manual and real R2/Drive rehearsal. This change requires targeted manual acceptance before release.

Since RPA-142 the active form asks Methodology per study. V2 stores the ordered `studies` directly: every study's question-number assignments, ordered methods, participant criteria and sample size remain separate. Overlapping studies and duplicate-looking answers are not combined or deduplicated.

Plan details asks whether other researchers are involved and, if so, their names (`otherResearchers`, `researcherNames`). The approved v2 policy includes those names when the answer is Yes and sends an empty names list when the answer is No. Browser email identity remains excluded.

Since RPA-119 who takes part in a study is one question, "Who should take part in this study?" (`characteristics`, named Participant criteria), where it was two lists (`characteristics` and `userGroups`). Historical user-group values remain readable and are folded into the active participant list by the plan model. V2 requires each study's active `methods` and `characteristics`; a historical dormant `userGroups` slot may be retained but is never a new requirement.

## Collection and validation

With the submissions capability enabled, task-list completion, Save and continue, and Send use `submission-contract.js`. Without the capability, the current draft-only journey remains available. The browser checks the rendered schema's keys, types, optional flags, per-question fields, table columns and choice values against the shared contract. A changed schema blocks sending rather than silently dropping a new active field. Requiredness changes need an explicit contract version and tests.

Required: title, project name, both roles, both plan dates, Context, Objective, whether other researchers are involved and their names when Yes, at least one research question and an outcome at each question index, at least one study, every question assigned to a study, all retained method/participant rows, a sample-size choice for every study, at least one complete schedule stage, both declarations and both sign-offs. Additional outcomes are retained without inventing associations. Every retained schedule row needs a valid stage or Other name, real ordered dates, and dates on or before the research readout. Valid generated defaults are accepted when the plan is complete and declared. Document creation (`createdAt`) is advisory. Word counts and AI scores are not gates.

Optional reference rows may have a name without a file. Meaningful file metadata requires a reference name. Files are never uploaded or fetched by submission; metadata may include an existing file name or link. Empty additional-information blocks are omitted from the network projection; partially filled blocks require both name and body. Older excess blocks are retained within the structural limits. Dormant legacy answers stay in browser drafts/backups and are excluded from submission. Exact authored strings and array order are preserved.

The independent server validator rejects unknown envelope/plan properties, unsupported schema/policy versions, unexpected cell types, invalid dates, arrays over 500 items and excessive property counts. JSON bodies are limited to 1 MiB with a 15-second body timeout. Pilot authentication and cross-site checks run before body listeners. The first slice supports only the existing protected pilot access mode; switching pilot mode off cannot open submissions. Separate in-memory limits allow five JSON submission attempts per minute across the shared pilot access and one in-flight attempt per submission ID. These are single-instance admission limits, not durable per-user or global quotas. AI limits are unchanged.

Other sample sizes use positive whole-number counts (`5`), ascending ranges (`5-8` or `5–8`), or minimums (`30+`). Zero, negative/fractional values and arbitrary text fail both client and server validation. Exact authored formatting remains in drafts/backups; these may retain values that are not ready for final submission. Existing local receipts and frozen retries are read structurally so a tightened rule cannot hide an earlier receipt; new or updated submissions still use current completion validation.

With submissions OFF, the same sample-size and schedule rules apply on Save and continue and before new browser-local signatures. They do not block draft saving or recovery. Existing signature history is preserved; older approvals are not retroactive proof that those versions enforced these checks. Reopen and correct a historical plan before signing a new revision.

Final sign-offs require initials followed by a real `DD/MM/YYYY` date. On a deliberate new Send, missing dates are added to the visible initials fields only when the corresponding declarations are checked, before the request is frozen. Importing/restoring a backup alone never adds an approval date. Existing dated sign-offs remain unchanged; pending retries keep their frozen payload and earlier local receipts remain readable. The server rejects undated or invalid new sign-offs. Dates remain user assertions rather than authenticated signatures; the server receipt time is recorded separately.

## Delivery and receipts

For v2, `POST /api/submissions` accepts exactly `submissionId`, `formSchemaVersion`, `collectionPolicyVersion`, `supersedesSubmissionId` and `plan`. `plan.planId` is stable across autosave and JSON backup/restore. Every deliberate Send/update gets a fresh `submissionId`; an update identifies the prior receipt it supersedes. The browser stores a frozen request before sending. A pending v1 or v2 snapshot is retried with the exact same ID and payload, even after edits or reload. Chrome's Web Locks serialise sending tabs on the same origin; conditional storage remains the duplicate guarantee for an ID. No account or cross-device deduplication is claimed.

R2 keys use server-selected deployment/cohort identifiers and UUIDs:

```
deployments/<deployment>/cohorts/<cohort>/cohort.json
deployments/<deployment>/cohorts/<cohort>/submissions/<uuid>.json
deployments/<deployment>/cohorts/<cohort>/deletions/<uuid>.json
```

Only `PutObject` with `If-None-Match: *` creates a submission. A private read-back verifies the record and SHA-256 of the canonical request before a `201` receipt. Same-ID/same-payload retries return the original timestamp and digest with `200`; changed content under the same ID returns `409` and never overwrites. Storage or read-back uncertainty returns `503` without a receipt. The browser retains the pending snapshot and explains that receipt is unconfirmed. `422` identifies a rejected incomplete plan; `410` means a deletion journal/tombstone prevents resurrection. Policy/version conflicts retain the reference for operator reconciliation.

New stored envelopes use record version 2 and contain server receipt time, application build, full-fidelity active plan, request digest, policy version and a durable cohort-policy reference. V2 receipts include receipt version, submission and plan IDs, schema, timestamp, digest, deployment and cohort. Historical v1 record/receipt shapes remain valid. No record contains browser credentials, attachment bytes, IP address or AI results. Declarations assert approval; they do not verify identity or constitute authenticated signatures. Sending does not clear the form. An updated submission is deliberate and requires both declarations again.

## Configuration and activation

Use the documented `.env.example` names in the hosting service's secret/settings controls. Do not upload a local `.env`. The runtime requires `RPA_SUBMISSIONS_ENABLED=true`, `RPA_SUBMISSIONS_ACCESS=pilot`, protected pilot configuration, explicit deployment/cohort IDs, a policy version, the full approved notice, and private R2 account/bucket/access credentials. Missing enabled configuration fails startup closed. The route also requires matching durable cohort metadata before its first write; configuration alone cannot create a cohort.

Choose and record the actual destination's jurisdiction/location before collecting real plans. Approve the operator names, purpose, permitted content, retention, deletion contact and access scope in `RPA_SUBMISSIONS_NOTICE`; the full notice appears before Send. The same notice/version must exist in `cohort.json`. There is no placeholder production notice and no invented final-session date. The cohort starts with `finalSessionAt` and `deleteAfter` set to null; close-out records the actual final-session timestamp and computes deletion after 28 days.

R2 public development URLs and custom domains must be disabled and verified. Use bucket-scoped server credentials. Use a separate read-only operator token for list/export, and a separately controlled read/write token for init, maintenance and deletion. R2 bucket read/write permission also permits deletion; the application credential is not an object-lock/WORM boundary. Restrict who can retrieve runtime secrets. Backups need independent access and storage, not another prefix in the same bucket. The CLI and server/storage files are never public assets and there is no HTTP list, retrieve or delete endpoint.

R2 Standard's free allowance is a costing assumption, not an enforced spend ceiling. Account billing, the actual region/jurisdiction, usage alerts and a usage ceiling/response owner must be verified before activation. RPA-80 retains that operating-cost decision. Do not alter the existing Anthropic workspace/key, model, budget or auto-reload settings for this feature.

Official implementation references: [R2 AWS SDK v3 configuration](https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/), [S3 compatibility and conditional writes](https://developers.cloudflare.com/r2/api/s3/api/), [consistency](https://developers.cloudflare.com/r2/reference/consistency/), [public-bucket controls](https://developers.cloudflare.com/r2/buckets/public-buckets/), [data security](https://developers.cloudflare.com/r2/reference/data-security/), [pricing](https://developers.cloudflare.com/r2/pricing/).

## Operator procedure

Run `node scripts/submissions.cjs --help` from the repository. Provide the selected cohort configuration and the appropriate operator token through a private operator process environment. Never pass credentials/passphrases as command-line arguments or write them into a shared script/log. Store an independent backup passphrase (at least 20 characters) in a password manager as `RPA_BACKUP_PASSPHRASE`; do not deploy it with the app.

`init-cohort` creates metadata conditionally and reads it back. `list` prints only reference/time/digest. `export-record UUID NEW_FILE.json` creates the full operator envelope. `export-plan UUID NEW_FILE.json` creates the collected plan; a v2 plan is also a version 11 JSON plan suitable for Restore. Historical v1 exports remain recoverable. These JSON files are plaintext and must go only to an approved protected operator folder. All exports create a new file exclusively, verify its bytes and return the file SHA-256. Existing files are never overwritten. A successful command proves that local file exists; it does not prove an independent copy has been made.

For backup, journal, pause/resume, deletion, close-out, purge or recovery: disable HTTP submission acceptance, drain in-flight sends (at least 75 seconds), stop other operator writes and set `RPA_SUBMISSIONS_MAINTENANCE=true` in the operator process. The drain covers the 15-second body limit and up to six private storage operations, each bounded to eight seconds including response-body consumption. The flag is an explicit operator attestation; it does not stop a running server. This prevents snapshots racing with collection/deletion. `cohort` displays the current durable metadata. `pause-cohort` also closes durable acceptance without declaring a final session. `resume-cohort` is explicit and refuses a cohort whose final session is recorded. Recovery never resumes acceptance automatically.

`backup NEW_FILE.rpa-encrypted` exports validated submissions, cohort metadata and deletion entries with AES-256-GCM encryption and a scrypt-derived key. `journal NEW_FILE.rpa-encrypted` exports metadata and deletions without plan contents. Keep an encrypted independent backup at the end of each collection day and after a session; verify its file hash and a decryption/recovery rehearsal before relying on it. Select and record the approved independent destination, backup owner and restore target before activation. The proposed recovery target is one working day; it has not been measured against a provider outage. Data received after the last independent backup remains exposed to loss of the primary destination.

`delete UUID NEW_JOURNAL.rpa-encrypted` writes an immutable deletion-journal entry first, then conditionally replaces the submission with a content-free tombstone and reads it back. Neither tombstone nor journal retains plan text or content digest. The command then creates a verified encrypted journal export. If interrupted, repeat the same UUID with a new output filename: the journal preserves intent and makes completion idempotent. Do not resume collection until the newest journal has reached the independent destination. Remove that UUID from existing plaintext/encrypted working exports and independent backups under the approved deletion process, or destroy/replace affected backup files. The CLI cannot delete copies in external folders or services; the operator must inventory and verify that work.

`close-cohort FINAL_SESSION_UTC NEW_JOURNAL.rpa-encrypted` records the actual UTC timestamp (for example the ISO format `YYYY-MM-DDTHH:mm:ss.sssZ`), closes collection and fixes the final-session-plus-28-days deadline. It refuses to silently change an existing final-session date. Record and assign the purge date immediately; this repository does not schedule a deletion job on the host. At the deadline, `purge-expired NEW_JOURNAL.rpa-encrypted` tombstones all primary submissions. Verify no content-bearing primary records remain, purge independent copies/working exports on the same deadline, and record those checks. Keep content-free tombstones/journals while a retry or older backup could still recreate a record; remove them only after collection is permanently closed and all content-bearing copies and pending recovery paths are retired.

To recover, keep acceptance disabled and pause the cohort. Verify the independent backup and newest independent deletion journal with their recorded hashes. `recover BACKUP.rpa-encrypted LATEST_JOURNAL.rpa-encrypted` verifies encryption, namespace, schemas and request digests, replays external and live deletion entries first, and restores only missing nondeleted records with their original IDs/receipt metadata. It refuses open collection, expired retention, older journals, corrupt records and conflicts. Recovery reconciles close-out dates across the backup, newest journal and live target before any write: a paused target cannot erase an independent final-session date or extend retention. Conflicting recorded final-session dates require operator reconciliation; a recovered finished cohort cannot resume. Existing records are never overwritten. A lost bucket can be reconstructed from those two exports with metadata closed. Confirm counts and sample plan restoration, reconcile browser pending references, then explicitly resume only if the cohort is still active. The operator must establish that the supplied journal is the newest independent copy; a program cannot infer that a newer external file exists.

## Evidence and release boundary

Automated tests use synthetic plans, injected R2 commands and a synthetic storage implementation. They exercise the real route and shared validator, conditional races, failure/read-back uncertainty, same-ID retry after a fresh Node process, deletion replay, encrypted backups, actual temporary export files with hashes, and restoration through the existing backup UI. DOM tests are not native-browser or real-R2 durability evidence.

Before activation, run a separately approved isolated provider exercise: conditional conflicts, private write/read-back, denied unauthenticated/public/list/read access, actual credential separation, restart/redeploy persistence, deletion/nonresurrection and recovery from the independent destination. Complete desktop/390 px keyboard checks against the implementation and record whether the preview used mocked storage. Finish the actual notice, region, destination, billing, backup owner and purge arrangements. RPA-1/RPA-6 own production deployment and pilot go/no-go; none occurs as a side effect of this ticket's local implementation.
